## 들어가며

[1편]({{ site.baseurl }}{% post_url 2026-11-21-kv-cache-routing-1-prefix-cache-and-routing %})에서는 프리픽스를 보고 라우팅하는 Go 프록시를 만들어 라운드로빈과 비교해보았습니다. 캐시 적중률이 0.71에서 0.90으로 올랐고, 부하가 높을수록 처리량 차이도 커졌습니다.

그런데 400줄 남짓의 프록시가 이 정도 결과를 낸다면, llm-d 같은 추론 스케줄러는 무엇이 더 나은 걸까 하는 의문이 남았습니다. 해서 이번에는 실험을 k3s로 옮기고, 같은 vLLM 파드 위에서 Go 프록시와 llm-d를 같은 부하로 비교해보았습니다.

결과를 먼저 말하면 평상시의 캐시 적중률은 거의 같았습니다. 차이는 라우터를 재시작했을 때와 파드 수를 바꿨을 때, 즉 운영 중에 실제로 일어나는 상황에서 나타났습니다.

## k3s로 옮기기

실험 환경은 집 PC에 이미 떠 있던 k3s 클러스터(노드 1개)를 사용했습니다. GPU는 1편과 같은 RTX 5070 Ti 한 장입니다.

Kubernetes는 GPU를 정수 개수로 세기 때문에, 노드에 `nvidia.com/gpu`가 1개뿐이면 GPU를 요청하는 파드는 하나만 올라갑니다. 해서 NVIDIA 디바이스 플러그인의 타임슬라이싱 설정으로 노드가 `nvidia.com/gpu=4`로 보이도록 두었습니다. 타임슬라이싱은 디바이스 플러그인이 GPU 개수를 부풀려서 알려 주는 소프트웨어 설정이고, MIG처럼 메모리를 나눠 주지는 않습니다. 해서 1편과 마찬가지로 vLLM마다 `--gpu-memory-utilization=0.22`로 상한을 걸어 주었습니다.

그 위에 올린 구성은 다음과 같습니다.

| 구성 요소 | 내용 |
|---|---|
| vLLM | StatefulSet 3개 (`vllm-0`, `vllm-1`, `vllm-2`), v0.33.0 |
| 라운드로빈 | Go 프록시 (`-policy=rr`) |
| Go 프록시 | 1편의 프리픽스 인지 프록시 (`-policy=prefix`) |
| llm-d 근사 | llm-d v1.0.0, 근사 프리픽스 스코어러 |
| llm-d 정밀 | llm-d v1.0.0, 정밀 프리픽스 스코어러 |

네 라우터가 같은 vLLM 파드 3개를 바라보고, 실험은 한 번에 한 라우터로만 부하를 보냈습니다. 실행마다 vLLM의 프리픽스 캐시를 비우고 라우터를 재시작해 인덱스도 비운 상태에서 시작했습니다.

llm-d는 standalone 차트로 설치했습니다. 라우터(Endpoint Picker)에 Envoy가 사이드카로 붙는 구성이고, 파드 목록은 `InferencePool`이라는 리소스로 관리합니다. gateway 차트도 있지만 클러스터의 Gateway API와 istio 버전을 올려야 해서 선택하지 않았습니다.

### 근사와 정밀

llm-d의 프리픽스 라우팅에는 두 가지 방식이 있습니다.

| | 근사 | 정밀 |
|---|---|---|
| 캐시 위치를 아는 방법 | 라우터가 어디로 보냈는지를 기억 | vLLM이 보내는 KV 캐시 이벤트를 구독 |
| 토큰화 | 하지 않음 | 요청마다 vLLM의 render 엔드포인트로 토큰화 |
| vLLM에 필요한 설정 | 없음 | `--kv-events-config`, `--enable-scale-out`, `--block-size=64` |

근사 방식은 1편의 Go 프록시와 원리가 같습니다. 보냈으니 거기 있을 것이라고 믿는 것이죠. 반면 정밀 방식은 vLLM이 블록을 저장하거나 지울 때마다 ZMQ로 발행하는 이벤트를 받아서, 실제로 어느 파드에 어떤 블록이 있는지를 인덱스로 만듭니다.

정밀 방식을 쓰려면 vLLM의 블록 크기를 라우터 설정과 같은 64토큰으로 맞춰야 했습니다. 1편의 docker compose 실험은 기본값인 16토큰이었기 때문에, 1편과 2편의 수치는 서로 비교할 수 없습니다. 이 글의 비교는 전부 k3s 위에서 같은 조건으로 잰 값끼리만 합니다.

그리고 llm-d의 필터에는 `peakPrefillThroughput`이라는 값이 들어가는데, 가이드의 값은 Qwen3-32B와 H100 기준이었습니다. 해서 파드 하나에 캐시에 없는 8,000토큰 프롬프트를 보내 TTFT를 잰 뒤(중앙값 390ms), 초당 약 20,500토큰으로 보정해서 넣었습니다.

## 예측

실험 전에 예상한 결과는 아래와 같습니다.

> 이 부하에서는 사실 큰 차이가 안 날 것 같다.
>
> Go 프록시와 llm-d 근사의 다른 점은, llm-d 쪽은 Envoy가 있어 홉이 하나 더 있으니 더 걸리지 않을까. Go 프록시는 하나의 프로세스에서 진행한다.

## 라우터 4종 비교

먼저 1편과 같은 기본 부하(대화 48개, 5턴, 동시 8, 시스템 프롬프트 4종)와, 시스템 프롬프트를 32종으로 늘린 부하를 보냈습니다. 조건마다 순서를 바꿔 가며 2번씩 돌렸습니다.

| 부하 | 정책 | 적중률 | 처리량 (tok/s) | TTFT p50 |
|---|---|---|---|---|
| 기본 | 라운드로빈 | 0.65~0.66 | 725~733 | 65~66ms |
| | Go 프록시 | 0.85 | 756~778 | 62~63ms |
| | llm-d 근사 | 0.84 | 764~776 | 61~64ms |
| | llm-d 정밀 | 0.85 | 757~767 | 69~70ms |
| 시스템 프롬프트 32종 | 라운드로빈 | 0.47~0.49 | 668~688 | 76~77ms |
| | Go 프록시 | 0.79 | 763~770 | 67~70ms |
| | llm-d 근사 | 0.79 | 759~772 | 71~77ms |
| | llm-d 정밀 | 0.79 | 755~762 | 76~87ms |

큰 차이가 안 날 것이라는 예측은 맞았습니다. 캐시를 보고 라우팅하는 세 가지는 적중률이 거의 같았고, 시스템 프롬프트 32종에서는 셋 다 0.79로 똑같이 나왔습니다. 라운드로빈만 0.47~0.49로 낮았습니다.

정밀 방식이 근사보다 적중률이 높지 않다는 점은 조금 의외였는데, 생각해보면 이 부하에서는 근사의 믿음이 틀릴 일이 없습니다. 캐시가 넉넉해서 블록이 밀려나지 않고, 파드도 그대로 떠 있으니 보낸 곳에 캐시가 그대로 남아 있는 것이죠. 근사의 믿음이 틀리는 상황은 뒤에서 따로 만들어 보았습니다.

## 부하를 올리면

동시 8은 GPU를 다 채우지 못하는 부하라서, 대화를 96개로 늘리고 동시 대화 수를 24와 48로 올려보았습니다.

| 동시 대화 수 | 정책 | 적중률 | 처리량 (tok/s) | TTFT p50 | TTFT p99 |
|---|---|---|---|---|---|
| 24 | 라운드로빈 | 0.71 | 1,684~1,729 | 88~89ms | 310~324ms |
| | Go 프록시 | 0.84~0.85 | 1,976~2,009 | 106~111ms | 245~254ms |
| | llm-d 근사 | 0.83 | 1,857~1,896 | 92~103ms | 350~352ms |
| | llm-d 정밀 | 0.85 | 1,945~1,957 | 123~128ms | 344~346ms |
| 48 | 라운드로빈 | 0.69 | 2,436~2,440 | 132~150ms | 464~472ms |
| | Go 프록시 | 0.84 | 3,179~3,203 | 170~189ms | 365~377ms |
| | llm-d 근사 | 0.82 | 2,865~2,962 | 137~180ms | 544~576ms |
| | llm-d 정밀 | 0.85 | 3,000~3,046 | 166~217ms | 542~559ms |

부하를 올리니 처리량에서 순위가 갈렸습니다. 동시 48에서 라운드로빈은 2,440 tok/s에 머물렀고, 캐시를 보는 세 가지는 2,865~3,203 tok/s가 나왔습니다. 그 안에서는 Go 프록시, llm-d 정밀, llm-d 근사 순이었습니다.

다만 이 순위를 가지고 Go 프록시가 llm-d보다 빠르다고 말하기는 어렵습니다. 조건당 2번씩만 돌렸고, 왜 이 순서가 되는지는 확인하지 못했습니다. 그리고 설명하지 못한 결과가 두 가지 더 있습니다. 첫 번째는 정밀 방식의 TTFT p50이 가장 높은 편이라는 점입니다 (동시 24에서 123~128ms). 요청마다 vLLM에 토큰화를 요청하는 비용일 수 있지만 따로 재 보지는 않았습니다. 두 번째는 동시 24에서 라운드로빈의 TTFT p50이 88~89ms로 가장 낮은데 처리량은 가장 낮다는 점입니다. 이 부분도 원인을 확인하지 못했습니다.

## 홉 오버헤드는 가리지 못했습니다

Envoy 때문에 llm-d가 더 느릴 것이라는 예측을 확인하려고, 부하와 캐시 변수를 빼고 경로만 보는 조건도 넣었습니다. 시스템 프롬프트 1종으로 요청 60개를 하나씩 순서대로 보냈고, 비교를 위해 라우터 없이 vLLM을 직접 호출한 경우도 같이 쟀습니다.

| 경로 | TTFT p50 |
|---|---|
| vLLM 직접 호출 | 22~37ms |
| 라운드로빈 | 40~63ms |
| Go 프록시 | 38~42ms |
| llm-d 근사 | 41ms |
| llm-d 정밀 | 45~46ms |

숫자만 보면 llm-d 정밀이 Go 프록시보다 몇 ms 느리지만, 이 측정으로는 결론을 내릴 수 없었습니다. 기준이 되는 직접 호출부터 실행마다 22ms에서 37ms까지 흔들렸기 때문입니다. 기준의 편차가 15ms인데 그 위에서 몇 ms 차이를 이야기할 수는 없으니, 이 예측은 맞았는지 틀렸는지 가리지 못했다고 적어 둡니다.

그리고 이 조건에서 정밀 방식은 요청을 한 파드로 모으지 않고 21 / 18 / 21로 흩어 보냈습니다. 프리픽스 일치율이 필터의 문턱을 넘지 못한 것으로 추정하고 있는데, 이것도 확인하지는 못했습니다.

## 라우터만 재시작하면

여기서부터는 근사의 믿음이 틀리는 상황을 만들어 보았습니다. 첫 번째는 라우터 재시작입니다. 시스템 프롬프트 32종 부하로 캐시를 채운 뒤, vLLM은 그대로 두고 라우터만 재시작해서 같은 대화를 다시 보냈습니다. vLLM의 캐시는 살아 있는데 라우터의 기억만 사라진 상황입니다.

실험 전 예측은 다음과 같았습니다.

> 재시작 이후에도 비슷하지 않을까. 결국 캐시가 채워지고 그걸로 라우팅하는 건 같다. 뭔가 달랐다면 아까 캐시 워밍 상태에서도 차이가 벌어졌을 것 같다.

| 정책 | 첫 턴 적중률 | 전체 적중률 |
|---|---|---|
| Go 프록시 | 0.71 | 0.86 |
| llm-d 근사 | 0.53~0.63 | 0.83~0.85 |
| llm-d 정밀 | 0.91 | 0.90 |

이 예측은 틀렸습니다. 대화의 첫 턴에서 차이가 났는데, 정밀 방식은 0.91을 유지한 반면 Go 프록시는 0.71, llm-d 근사는 0.53~0.63으로 떨어졌습니다.

근사 방식은 보낸 기록이 라우터의 메모리에만 있기 때문에, 재시작하면 어느 파드에 무엇이 있는지를 전부 잊게 됩니다. 해서 첫 턴은 캐시가 없는 파드로 가는 경우가 생깁니다. 반면 정밀 방식은 재시작 후에 vLLM 파드들의 이벤트를 다시 구독하고, vLLM이 열어 둔 재전송(replay) 소켓으로 지금 캐시에 있는 블록 정보를 다시 받아 옵니다. 라우터가 죽었다 살아나도 캐시의 위치를 아는 것이죠.

다만 2턴부터는 세 가지가 다시 같아졌습니다 (0.85~0.92). 근사 방식도 첫 턴을 보내면서 기록이 다시 쌓이기 때문입니다. 해서 전체 적중률의 차이는 0.04~0.07 정도였습니다. 라우터 재시작의 영향은 재시작 직후의 요청에 한정된다고 볼 수 있습니다.

참고로 같은 실험에서 라운드로빈의 첫 턴 적중률은 0.87~0.91로 높게 나왔습니다. 캐시를 채울 때 라운드로빈이 모든 프리픽스를 세 파드에 골고루 뿌려 놓았기 때문이고, 라우팅이 좋아서 나온 값은 아닙니다. 그리고 llm-d 근사가 Go 프록시보다 더 낮게 나온 이유는 확인하지 못했습니다.

## 파드 수를 바꾸면

두 번째는 파드 수 변경입니다. 파드 3개에서 캐시를 채운 뒤, 라우터는 그대로 둔 채 StatefulSet을 2개로 줄였다가 다시 3개로 늘렸습니다. 다시 뜬 `vllm-2`는 이름은 같지만 캐시가 비어 있는 새 파드입니다. 이 실험은 정책당 1번씩만 돌렸습니다.

### 3개에서 2개로

| 정책 | 요청 | 오류 | 적중률 | 파드별 요청 (vllm-0 / 1) |
|---|---|---|---|---|
| Go 프록시 | 180 | 15 | 0.89 | 90 / 75 |
| llm-d 근사 | 240 | 0 | 0.86 | 125 / 115 |
| llm-d 정밀 | 240 | 0 | 0.86 | 115 / 125 |

Go 프록시에서만 502 오류가 15건 발생했습니다. Go 프록시는 백엔드 목록을 시작할 때 인자로 받아서 고정해 두기 때문에, 사라진 `vllm-2`로 계속 요청을 보낸 것입니다. 부하 생성기는 오류가 난 대화를 거기서 중단하므로 전체 요청 수도 240건이 아니라 180건이 됐습니다.

반면 llm-d는 오류가 없었습니다. `InferencePool`로 파드의 변화를 따라가기 때문에 `vllm-2`가 사라지자 남은 두 파드로 요청을 다시 나눴습니다.

### 다시 3개로

| 정책 | 오류 | 적중률 | 라우터가 예측한 적중률 | 파드별 요청 (vllm-0 / 1 / 2) |
|---|---|---|---|---|
| Go 프록시 | 0 | 0.86 | 0.93 | 90 / 75 / 75 |
| llm-d 근사 | 0 | 0.90 | 0.90 | 125 / 115 / 0 |
| llm-d 정밀 | 0 | 0.90 | 0.90 | 115 / 125 / 0 |

파드가 다시 뜨자 Go 프록시의 오류는 사라졌지만, 이번에는 다른 문제가 보였습니다. Go 프록시는 새로 뜬 빈 `vllm-2`로 75건을 보냈습니다. 예전 `vllm-2`로 보낸 기록이 그대로 남아 있어서, 이름이 같은 새 파드에도 캐시가 있다고 믿은 것입니다. 프록시가 예측한 적중률은 0.93이었는데 실제는 0.86이었고, 첫 턴 적중률은 0.71까지 떨어졌습니다.

llm-d는 근사와 정밀 모두 새 파드로 한 건도 보내지 않았고 적중률 0.90을 유지했습니다. 라우터가 예측한 적중률도 실제와 같은 0.90이었으니, 근사 방식도 사라진 파드에 대한 기록을 그대로 믿고 있지는 않았던 것으로 보입니다.

### 새 파드는 안 쓰이는 걸까

그런데 새 파드로 0건이라는 결과는 조금 이상해 보였습니다. 파드를 늘렸는데 아무 요청도 가지 않는다면 늘린 의미가 없으니까요. 해서 처음 보는 프리픽스로 된 대화를 새로 보내보았습니다.

| 정책 | 적중률 | 파드별 요청 (vllm-0 / 1 / 2) |
|---|---|---|
| llm-d 근사 | 0.79 | 85 / 75 / 80 |
| llm-d 정밀 | 0.91 | 85 / 75 / 80 |

이번에는 `vllm-2`도 80건을 받았습니다. 새 파드가 풀에서 빠져 있던 것이 아니라, 앞의 대화들은 캐시가 있는 파드에 붙여 두었던 것입니다. 1편에서 본 캐시와 분산 사이의 긴장이 여기서도 그대로 나타났습니다. 캐시를 따라가는 정책에서는 파드를 늘려도 기존 대화의 부하는 새 파드로 넘어가지 않습니다.

이 표에서 정밀의 적중률이 0.91로 높은 것은 순서 때문입니다. 근사 라우터로 먼저 보낸 대화를 곧이어 정밀 라우터로 다시 보냈기 때문에 캐시가 이미 차 있었습니다. 같은 조건의 비교는 아니지만, 정밀 방식은 다른 라우터가 만들어 놓은 캐시도 이벤트를 통해 알고 있다는 점은 확인할 수 있었습니다.

## 마무리

Go 프록시와 llm-d가 무엇이 다른지에 대해 2편에서 확인한 것은 다음과 같습니다.

| 상황 | 결과 | 근거 |
|---|---|---|
| 평상시의 캐시 적중률 | 같다 | 기본 0.84~0.85, 32종은 셋 다 0.79 |
| 부하가 높을 때의 처리량 | 캐시를 보는 셋이 라운드로빈보다 높다. 셋 사이의 순위는 원인 미확인 | 동시 48에서 2,440 대 2,865~3,203 tok/s |
| Envoy 홉의 오버헤드 | 가리지 못함 | 직접 호출이 실행마다 22~37ms |
| 라우터 재시작 직후 | 정밀만 유지 | 첫 턴 0.91 대 0.71, 0.53~0.63 |
| 파드가 줄었을 때 | Go 프록시만 오류 | 502 오류 15건 |
| 파드가 다시 늘었을 때 | Go 프록시만 빈 파드를 믿음 | 예측 0.93 대 실제 0.86 |

프리픽스를 보고 라우팅하는 것 자체는 400줄로도 되고, 이 규모에서는 정확도도 llm-d와 같았습니다. llm-d가 해 주는 일은 그 바깥에 있었습니다. 파드가 늘고 줄 때 목록을 따라가고, 사라진 파드를 더 이상 믿지 않고, 정밀 방식이라면 라우터가 재시작해도 캐시의 위치를 다시 알아냅니다. Kubernetes에서 서빙을 운영한다면 매일 일어나는 일들이고, 이걸 따로 구현하려면 프리픽스 매칭보다 이쪽에 손이 훨씬 많이 갈 것 같습니다.

물론 한계도 있습니다.

- 1편과 마찬가지로 GPU 한 장을 파드 3개가 나눠 쓰는 구성입니다.
- 4종 비교와 재시작 실험은 2번씩, 파드 수 변경 실험은 1번씩만 돌렸습니다.
- llm-d의 라우터는 1개만 띄웠습니다. 라우터를 여러 개 띄웠을 때의 동작은 보지 않았습니다.
- prefill과 decode를 분리해서 서빙하는 기능처럼 llm-d가 제공하는 다른 기능은 써 보지 않았습니다.

그리고 한 가지가 더 남았습니다. 이번 실험에서는 캐시가 넉넉해서 블록이 밀려나는 일이 없었고, 그래서 근사와 정밀의 차이도 재시작 직후에만 보였습니다. 다음 **3편** 에서는 GPU 캐시를 일부러 줄여서 프리픽스가 밀려나는 상황을 만들고, 밀려난 캐시를 CPU 메모리에 옮겨 두는 KV 오프로딩을 켰을 때 무엇이 달라지는지 확인해보겠습니다.
